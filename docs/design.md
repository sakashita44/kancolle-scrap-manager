# 艦これ 工廠任務廃棄マネージャー 仕様書

## プロジェクト概要

- 名称: 艦これ 工廠任務廃棄マネージャー (Kancolle Scrap Manager)
- 目的: 複数の工廠任務(廃棄任務)を並列遂行する際, 廃棄すべき装備の必要最小限のリスト(最適解)を算出し, 無駄な廃棄を防ぐ.
- 提供形態: 静的Webアプリケーション (Single Page Application)
- ライセンス: MIT License

## システムアーキテクチャ

### 構成

サーバーレスな静的サイト構成を採用し, 運用コストを最小化する.

| 要素        | 技術スタック                          | 役割                                     |
| :---------- | :------------------------------------ | :--------------------------------------- |
| Frontend    | React, Tailwind CSS, Lucide React     | UI/UX, 計算ロジックの実行                |
| Language    | TypeScript (strict)                   | 型安全性                                 |
| State       | Zustand (単一Store, slice構成)        | 状態管理                                 |
| Validation  | Zod v4                                | スキーマベースバリデーション             |
| Form        | react-hook-form + @hookform/resolvers | 宣言的フォーム管理                       |
| Build       | Vite                                  | ビルドツール                             |
| Testing     | Vitest                                | 純粋関数の回帰テスト                     |
| Hosting     | ロリポップ (Lolipop)                  | ビルド済み静的ファイルの配信             |
| Master Data | アプリケーションバンドル              | 公式マスタデータ (.json) をバンドル      |
| Database    | LocalStorage (Browser)                | ユーザー定義データ, 設定, 選択状態の保存 |

### 状態管理設計

単一のZustand storeを3つのsliceに分割し、コンポーネントはセレクタ経由でstoreに直接アクセスする（Contextプロバイダは不要）.

- **dataSlice** (`src/store/dataSlice.ts`): カテゴリ・装備・任務のCRUD, LocalStorage永続化, 起動時バリデーション
- **selectionSlice** (`src/store/selectionSlice.ts`): 任務選択状態(ベース/補助), SessionStorage永続化
- **uiSlice** (`src/store/uiSlice.ts`): フィルタ, 展開/折りたたみ, モーダル, SessionStorage永続化

### データフロー

マスタデータをアプリケーションにバンドルする戦略を採用し、起動時のネットワーク待機をゼロにする。

1. 起動時 (Load Master Data):
    - マスタデータ (`src/data/*.json`) はビルド時にアプリケーションバンドルに含まれる。
    - `App.tsx` で直接インポートし、`source: "master"` をランタイムで付与。
    - 利点:
        - アプリとマスタデータのバージョン不整合を完全に防ぐ。
        - ネットワーク待機時間がゼロ（即座に起動）。
        - フェッチエラー、タイムアウト、フォールバック処理が不要。
1. LocalStorageデータのバリデーション:
    - 目的: LocalStorage直接編集やブラウザ拡張機能による破損、古いバージョンのアプリで作成されたデータなど、外部要因によるデータ破損を検出し自動修復する。
    - `src/store/storage.ts` の `loadUserCategories()` / `loadUserEquipments()` / `loadUserMissions()` で全ユーザー定義データをZodスキーマにより個別バリデーション。
    - バリデーション失敗したデータは除外し、正常なデータのみで状態を初期化。
    - 破損データが存在した場合、`dataWarnings` に記録しグローバル警告バナーに表示（エラーレベル: Warning）。
1. マージ:
    - 公式マスタとユーザー定義データ(バリデーション済み)をメモリ上で結合.
    - ID重複時: 読み込み順(ユーザー定義優先)で処理するか, エラーログに記録して続行する(クラッシュさせない).

保存:

- ユーザー操作(追加・削除・チェック)のたびに`LocalStorage`へ即時保存.
- エラー処理: `try-catch`で囲み, 容量オーバー時やプライベートモード制限時はアラートで通知.
- 競合対策: `storage`イベントを監視し, 他タブでデータが更新された場合は「データが更新されました. リロードしてください」と通知バーを表示する(データの自動マージは行わない).

## データ構造・ID規則

データの競合を防ぐため, IDのプレフィックスによる名前空間管理を行う.

### ID規則と生成ロジック

| データ種別       | ID接頭辞 | 生成ルール     | 削除 | 備考                               |
| :--------------- | :------- | :------------- | :--- | :--------------------------------- |
| 公式マスタ       | `m_`     | `m_<文字列>`   | 不可 | 手動定義. リリース後のID変更は禁止 |
| ユーザーカテゴリ | `u_cat_` | `u_cat_<UUID>` | 可   | UUID v4生成                        |
| ユーザー装備     | `u_eq_`  | `u_eq_<UUID>`  | 可   | UUID v4生成                        |
| ユーザー任務     | `u_ms_`  | `u_ms_<UUID>`  | 可   | UUID v4生成                        |

環境要件:

- `crypto.randomUUID()`を使用するため, HTTPS環境 (SSL) または`localhost`での動作を必須とする.

バリデーション:

- インポート時, IDのプレフィックス (`m_`, `u_cat_`, `u_eq_`, `u_ms_`) が仕様通りか検証.
- 不正な形式やJSON構文エラーがある場合, 読み込みを中断・破棄し, エラーを表示する.

### マスタデータ定義

共通フィールド: 各JSONファイルのルートには`version`(スキーマバージョン)を含める.

装備データ (Equipment)

| カラム       | 型     | 説明                               |
| :----------- | :----- | :--------------------------------- |
| `id`         | String | ID規則に従う                       |
| `name`       | String | 装備名                             |
| `categoryId` | String | 所属カテゴリID (例: "m_cat_gun_s") |
| `order`      | Number | 表示順序                           |

任務データ (Mission)

| カラム   | 型     | 説明                                                             |
| :------- | :----- | :--------------------------------------------------------------- |
| `id`     | String | ID規則に従う                                                     |
| `name`   | String | 任務名                                                           |
| `period` | Enum   | Daily / Weekly / Monthly / Quarterly / Yearly / OneTime          |
| `order`  | Number | 表示順序                                                         |
| `reqs`   | Array  | 要求装備リスト [{ kind: "equipment", id: "m_eq_...", count: 3 }] |

## ロジック仕様

### 計算ロジック

- 事前チェック: 選択任務が0件の場合は, 計算結果(廃棄リスト)も0件とする.
- 展開と整合性:
    - 選択された全任務の要求装備を展開.
    - `id`がマスタに存在しない場合, その要求は計算から除外(廃棄数0)し, 該当任務に警告アイコンを表示する.
- 最大値判定 (MAX): 同一装備IDに対する要求は, 合計ではなく最大値を採用.
- 包含解決 (OR条件): カテゴリ指定数から個別装備指定数を差し引いて残数を算出.
- 制限: 同時選択可能な任務数は, ゲーム内仕様に合わせ最大8つまでとする(UI制御).

### サポート対象外の任務

本アプリは「効率的な廃棄リストの最適化」を目的としているため, 以下の特性を持つ任務はサポート対象外とする:

- 「なるべく多く廃棄」タイプの任務 (例: ウィークリー任務「資源の再利用」)
    - 理由: 計算支援の必要性が低い.
    - 対応: About画面に「サポート対象外」として明記する. 将来的に同タイプの任務が増加した場合は対応を再検討する.

## UI/UX 仕様

### レイアウト

- Header: アプリ名, 設定メニュー.
- Global Warning Banner: データ破損検出時等の警告表示.
- 任務ペイン: Control Bar(フィルタ, 追加ボタン), Mission List(任務一覧).
- 結果パネル: 廃棄リスト, ベース任務の達成状況, 選択中の任務. 画面幅1024px以上では右カラムに固定表示し, それ未満では画面上部に固定表示する.

### インポート/エクスポート

- フォーマット: 装備と任務で分割されたJSON(マスタデータと同じ構造).
- エクスポート:
    - 装備データ(`kancolle_scrap_equipments_YYYYMMDD.json`)と任務データ(`kancolle_scrap_missions_YYYYMMDD.json`)を別々にダウンロード.
    - 両方または片方のみのエクスポートが可能.
- インポート挙動:
    - ファイル内容から装備/任務を自動判別(`equipments`配列または`missions`配列の存在で判定).
    - Zodスキーマでバリデーションを行い, 問題なければ該当タイプの既存データを全上書きする(事前警告あり).
    - 装備のみ,任務のみの部分インポートが可能.
- 選択状態: SessionStorageに保存し,タブ/ウィンドウを閉じると消去される.

### ユーザー入力フォーム詳細と制限

入力バリデーションは「送信後のエラー表示」ではなく, 「条件を満たすまで保存ボタンを無効化 (Disabled) する」モダンなUXを採用する.

A. 装備追加フォーム

| 項目     | UI要素              | バリデーション・制限                   |
| :------- | :------------------ | :------------------------------------- |
| 装備名   | テキストボックス    | 必須. 最大文字数: 40文字. 同名警告あり |
| カテゴリ | テキスト + Datalist | 必須. 最大文字数: 20文字               |

B. 任務追加モーダル

| 項目     | UI要素                | バリデーション・制限                           |
| :------- | :-------------------- | :--------------------------------------------- |
| 任務名   | テキストボックス      | 必須. 最大文字数: 50文字                       |
| 周期     | プルダウン            | 必須 (Weekly等)                                |
| 要求装備 | プルダウン            | 必須. 既存装備リストから選択. 最大10件まで追加 |
| 必要数   | スピンボタン (Number) | 必須. 1〜30の整数                              |

## 運用・開発フロー

### バージョニング戦略

Semantic Versioning (vX.Y.Z) を採用する.

- Major (X): データスキーマの変更(互換性なし). マイグレーション処理が必要.
- Minor (Y): 機能追加, 公式マスタへの任務追加.
- Patch (Z): バグ修正, 誤字訂正.

### マイグレーション戦略 (Future Scope)

現時点ではコンバータは実装しないが, 以下のルールで将来の変更に備える.

- バージョン保持: 保存データ(`LocalStorage`/JSON)には必ず`version`フィールドを含める.
- ロード時判定: アプリ起動時にデータの`version`をチェック.
- アプリの対応バージョンより古い場合, 将来的に変換ロジックを通すか, 初期化を促すアラートを出す.

### セキュリティ・プライバシー

- HTTPS必須: `crypto.randomUUID`等のAPI利用および通信経路保護のため, 本番環境はSSL化を必須とする.
- バックエンドレス: ユーザーデータは全てブラウザ内に保存され, 外部サーバーへ送信されないことをAbout画面等に明記する.
- XSS対策: Reactの標準エスケープ機能に依存し, `dangerouslySetInnerHTML`は使用しない. 入力値はZodスキーマで危険パターンを検出・拒否する.

### その他

- アクセシビリティ: 初期リリースでは考慮外とし, 将来的な対応課題とする.
- 多言語化: 初期リリースでは非対応.

### 運用ルール (Developer)

- ID不変: 公式マスタデータのIDは, 一度リリースしたら変更・削除しない(ユーザーデータの参照切れを防ぐため). 廃止したい場合は, 名称を「【廃止】...」とする等の論理削除で対応する.

#### ディレクトリ構成とデプロイ

- 配置場所: マスタデータは必ず `src/data/` ディレクトリに配置する。
    - 理由: ビルドツール (Vite) によってアプリケーションバンドルに含まれるため。

- デプロイ手順:
    1. `npm run build` を実行。
    1. 生成された `dist/` フォルダの中身をロリポップへアップロード。

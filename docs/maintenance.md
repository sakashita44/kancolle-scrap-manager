# 保守・運用ドキュメント

## マスタデータ更新ルール

### Order番号の割り振りルール

マスタデータ（公式装備・任務）のorder値は以下のルールに従って設定する.

#### 装備データ (equipments.json)

**Category型（カテゴリ代表装備）**:

* 1番から順に採番: 1, 2, 3, 4...
* 例: 小口径主砲（種別不問）= 1, 中口径主砲（種別不問）= 2

**Item型（個別装備）**:

* カテゴリごとに100番台で区切る
* 小口径主砲: 100, 101, 102...
* 中口径主砲: 200, 201, 202...
* 大口径主砲: 300, 301, 302...
* 機銃: 400, 401, 402...
* 魚雷: 500, 501, 502...
* 爆雷: 600, 601, 602...
* ソナー: 700, 701, 702...
* 艦上戦闘機: 800, 801, 802...
* 艦上爆撃機: 900, 901, 902...
* 艦上攻撃機: 1000, 1001, 1002...
* 艦上偵察機: 1100, 1101, 1102...

**ユーザー定義装備**:

* 0番から順に自動採番（カテゴリに関係なく通し番号）
* アプリケーションが自動的に `Math.max(...userEquipments.map(e => e.order)) + 1` を計算

**表示順序**:

1. `isMaster` フラグ（公式マスタが先、ユーザー定義が後）
2. `order` 値の昇順

結果的に以下の順序で表示される:

```text
公式Category型 (order: 1, 2, 3...)
公式Item型 (order: 100, 101, 200, 201...)
ユーザー定義装備 (order: 0, 1, 2...)
```

#### 任務データ (missions.json)

**マスタ任務**:

* `period` (Daily/Weekly/Monthly/Quarterly/Yearly/OneTime) ごとにグループ化
* 各期間内で `order` 値の昇順にソート
* 期間ごとに0から採番（例: Daily任務は0, 1, 2...、Weekly任務も0, 1, 2...）

**ユーザー定義任務**:

* 0番から順に自動採番（期間に関係なく通し番号）
* 同一period内での順序のみ意味を持つ

### データ追加時のチェックリスト

新しいマスタデータを追加する際は以下を確認する:

* [ ] `id` が一意であること（既存IDと重複しない）
* [ ] `id` のプレフィックスが正しいこと（マスタ: `m_`, ユーザー: `u_`）
* [ ] `order` 値が上記ルールに従っていること
* [ ] 必須フィールドが全て含まれていること（schema.md参照）
* [ ] `isMaster` フラグは**JSON内に記述しない**（ランタイムで自動付与される）
* [ ] バリデーションが通ること（アプリ起動時にコンソールでエラー確認）

### データ削除・非推奨化

**重要**: 一度公開したマスタデータのIDは変更・削除してはならない. ユーザーのローカルデータが参照している可能性があるため.

非推奨化する場合:

* IDはそのまま残す
* `name` を "【廃止】..." に変更
* 必要に応じて `order` を末尾に移動

npm run build

* `dist/` フォルダが生成される
* `public/data/` 内のマスタデータも `dist/data/` にコピーされる

### 本番環境へのアップロード

1. Lolipopへの静的ファイルアップロード
   * `dist/` フォルダの内容を本番サーバーにアップロード
   * バックアップマスタデータ（`dist/data/*.json`）が含まれる

2. GitHub Pagesへのマスタデータ公開
   * `public/data/` の変更をコミット・プッシュ
   * GitHub Pagesが自動的に更新される
   * プライマリマスタデータとして機能

### キャッシュバスティング

マスタデータのURL末尾にバージョンクエリパラメータを付与する:

```text
https://<user>.github.io/.../data/equipments.json?v=1.0.0
```

バージョン更新時は `src/utils/dataFetch.js` 内のバージョン文字列を更新する.

## バージョン管理

### スキーマバージョン

各JSONファイルの `version` フィールドはSemantic Versioningに従う:

* MAJOR: 互換性のない変更（フィールド削除、型変更）
* MINOR: 後方互換性のある機能追加（新フィールド追加）
* PATCH: バグ修正、データ更新

**重要**: 現在のアプリはバージョン番号を検証しない. スキーマ構造のみバリデーションする. バージョンは人間用の情報として扱う.

### スキーマ変更時の注意

* 既存フィールドの削除・型変更は**禁止**（MAJOR変更となり互換性が失われる）
* 新フィールド追加は**可能**（MINOR変更、既存データに影響なし）
* 新フィールドには適切なデフォルト値を設定すること

## トラブルシューティング

### マスタデータバリデーションエラー

起動時にバリデーションエラーが発生した場合:

1. ブラウザのコンソールでエラーログを確認
2. `docs/schema.md` でフィールド定義を確認
3. 該当JSONファイルを修正
4. アプリを再起動してエラーが解消されたか確認

### ユーザーデータ破損

LocalStorageに保存されたユーザーデータが破損した場合:

* アプリは自動的に破損データを削除する
* Global Warning Bannerに削除されたアイテムの詳細が表示される
* ユーザーはエクスポート機能（issue #12）でバックアップを取ることを推奨

### GitHub Pagesフェッチ失敗

プライマリマスタデータ（GitHub Pages）の取得に失敗した場合:

* 自動的にローカルバックアップ（`./data/*.json`）にフォールバックする
* Global Warning Bannerに警告が表示される
* アプリは通常通り動作する

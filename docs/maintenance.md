# 保守・運用ドキュメント

マスタデータを更新し、版数を判断してアプリを公開するための規則と手順をまとめる。更新ルールと版数の判定基準を確認した後、リリース・デプロイの手順に進み、公開結果を照合する。

## マスタデータ更新ルール

### Order番号の割り振りルール

マスタデータ（公式装備・任務）のorder値は、次の規則に従って設定する。

#### 装備データ (equipments.json)

**公式装備**:

- 装備の `order` は「所属カテゴリの `order` 値 × 100」を基点とし、カテゴリ内で連番を振る
- 例: 大口径主砲（カテゴリ `order` = 3）の装備は 300, 301, 302...
- 例: 艦上戦闘機（カテゴリ `order` = 6）の装備は 600, 601, 602...
- 新カテゴリを追加した場合、そのカテゴリの `order` × 100 が装備の基点になる

**ユーザー定義装備**:

- 0番から順に自動採番（カテゴリに関係なく通し番号）
- アプリケーションが自動的に `Math.max(...userEquipments.map(e => e.order)) + 1` を計算

**表示順序**:

1. `source`（`"master"` が先、`"user"` が後）
1. `order` 値の昇順

結果的に以下の順序で表示される:

```text
公式装備 (order: 100, 101, 200, 201...)
ユーザー定義装備 (order: 0, 1, 2...)
```

#### 任務データ (missions.json)

**マスタ任務**:

- `period` (Daily/Weekly/Monthly/Quarterly/Yearly/OneTime) ごとにグループ化
- 各期間内で `order` 値の昇順にソート
- 期間ごとに0から採番（例: Daily任務は0, 1, 2...、Weekly任務も0, 1, 2...）

**ユーザー定義任務**:

- 0番から順に自動採番（期間に関係なく通し番号）
- 同一period内での順序のみ意味を持つ

### データ追加時のチェックリスト

新しいマスタデータを追加する際は以下を確認する:

- [ ] `id` が一意であること（既存IDと重複しない）
- [ ] `id` のプレフィックスが正しいこと（マスタ: `m_`, ユーザー: `u_`）
- [ ] `order` 値が[Order番号の割り振りルール](#order番号の割り振りルール)に従っていること
- [ ] 必須フィールドが全て含まれていること（schema.md参照）
- [ ] `source` フィールドは**JSON内に記述しない**（ランタイムで `"master"` / `"user"` が自動付与される）
- [ ] 装備・カテゴリの種別がゲーム内の装備種別と一致していること（艦これWiki準拠）
- [ ] 任務が参照する装備・カテゴリがマスタに存在すること（新装備が必要なら先に追加する）
- [ ] `npm run validate:data` が通ること（参照整合性・ID一意性を検証）
- [ ] [マスタデータ更新日と告知](#マスタデータ更新日と告知)に従い、更新日を記録し、告知を差し替えること

任務が要求する装備が既存カテゴリのどれにも該当しない場合、装備を既存カテゴリへ押し込めず、ゲームの装備種別に対応する新カテゴリを追加する（カテゴリの `order` は末尾に採番）。

### データ削除・非推奨化

ユーザーのローカルデータが参照している可能性があるため、一度公開したマスタデータのIDは変更・削除してはならない。

非推奨化する場合:

- IDはそのまま残す
- `name` を "【廃止】..." に変更
- 必要に応じて `order` を末尾に移動

### マスタデータ更新日と告知

バナーの告知文はすべて `src/data/notices.json` に集約し、コンポーネント（`.tsx`）へ直書きしない。`type` は critical / error / warning / info から選ぶ。

マスタデータの最終更新日は `src/data/masterDataMetadata.json` の `updatedAt`（`YYYY-MM-DD`）で管理し、Aboutに表示する。カテゴリ・要求カテゴリグループ・装備・任務の内容を変更した際に、実際の更新日を記録する。ビルド、再デプロイ、告知のみの変更では更新しない。

更新告知は `src/data/notices.json` の `master_data_update` に集約し、`type: "info"` で日付と変更内容を記載する。追加件数と日付はマスタデータの差分・更新記録と照合する。

更新告知の掲載は次のマスタデータ更新までとし、その更新を公開する際に前回の告知を新しい告知へ差し替える。マスタデータを変更しないリリースでは継続して掲載する。恒常的な注意書きは更新告知の差し替え対象に含めない。

更新日は同梱データ全体の更新時点を示し、各任務のゲーム内実装日や、全データを再確認した日を示すものではない。

マスタデータの更新告知のほかに、版数固有の新機能や注意事項も告知できる。版数固有の告知はリリース時に見直し、用済みであれば削除する。

## バージョン管理

### アプリバージョン

アプリの版数は `package.json` の `version` で管理する。`vite.config.ts` がビルド時に `__APP_VERSION__` として注入し、Aboutモーダルに表示される。バージョンを更新する際は `package.json` のみを変更する。

### アプリ版数の判定基準

アプリとマスタデータを同梱して配布する構成では、リリースに含まれる変更のうち最も大きい区分を適用する。

| 変更内容                                                                     | 版数  |
| :--------------------------------------------------------------------------- | :---- |
| 既存形式での任務・装備の追加、データ訂正、不具合修正、更新日・更新告知の表示 | patch |
| 計算・操作など利用者が使える機能の追加                                       | minor |
| 公開契約や保存データ形式の互換性を失う変更                                   | major |

コミットの `feat` やCHANGELOGの `Added` だけを理由にminorと判定しない。データの鮮度は[マスタデータ更新日](#マスタデータ更新日と告知)で示す。この基準はアプリの運用方針であり、各JSONのスキーマ版数とは区別する。

### スキーマバージョン

各JSONファイルの `version` フィールドはSemantic Versioningに従う:

- MAJOR: 互換性のない変更（フィールド削除、型変更）
- MINOR: 後方互換性のある機能追加（新フィールド追加）
- PATCH: バグ修正、データ更新

アプリはスキーマ構造のみを検証し、バージョン番号は検証しない。バージョン番号は人間向けの情報として扱う。

### スキーマ変更時の注意

- 既存フィールドの削除・型変更は**禁止**（MAJOR変更となり互換性が失われる）
- 新フィールド追加は**可能**（MINOR変更、既存データに影響なし）
- 新フィールドには適切なデフォルト値を設定すること

## リリースとデプロイ

### リリース前のチェックリスト

公開前に、版数・告知・動作と自動検証の結果を確認する:

- [ ] アプリバージョン: `package.json` の `version` のみを更新する（About表示・ビルドへ `__APP_VERSION__` として自動注入されるため他ファイルの手修正は不要）
- [ ] [告知の管理規則](#マスタデータ更新日と告知)に従い、`notices.json` を見直す。用済みになった特定バージョンの告知を削除し、新規告知があれば追加する
- [ ] マスタデータの変更がある場合は、[マスタデータ更新日と告知](#マスタデータ更新日と告知)に従い更新日・件数と告知の差し替えを確認する
- [ ] [アプリ版数の判定基準](#アプリ版数の判定基準)に従い、リリース全体の変更内容から版数を決定すること
- [ ] `CHANGELOG.md` の `[Unreleased]` を確認し、必要ならバージョン見出しへ昇格する
- [ ] `npm run validate:data` が通ること
- [ ] 初回訪問でAboutが自動表示され、再訪問では自動表示されず、メニューから再表示できること。通常のデータ更新では `ksp_about_shown` をリセットしない
- [ ] ユーザー定義データと選択状態が保持され、`npm test`、`npm run lint`、`npm run build` が通ること

### リリース手順

バージョンを上げる際は以下の順で行う。リリースコミット（`chore: リリースx.y.z`）は作業ブランチ内で作成し、`main` へマージした後にタグを打つ（過去リリースの慣行に一致）。

作業前に[アプリ版数の判定基準](#アプリ版数の判定基準)で版数を決め、[リリース前のチェックリスト](#リリース前のチェックリスト)を確認する。

1. **作業ブランチ内でリリースコミットを作る**
    - `CHANGELOG.md` の `[Unreleased]` を `## [x.y.z] - YYYY-MM-DD` へ昇格し、新しい空の `[Unreleased]` を先頭に残す
    - `package.json` の `version` を `x.y.z` へ更新する
    - このコミットには `CHANGELOG.md` と `package.json` のみを含める（コミットメッセージは `chore: リリースx.y.z`）
1. **PRを作成し `main` へマージする**（マージコミット。squash / rebase は禁止）
1. **マージ後、`main` のマージコミットにタグを打つ**
    - `git tag vx.y.z`（タグ名は `v` 接頭辞。既存タグの命名に一致させる）
    - `git push --follow-tags`
1. **GitHub Release を作成する**
    - `gh release create vx.y.z` の notes に `CHANGELOG.md` の当該バージョンセクションを渡す
    - 版数判定・反映は `/release` スキルで自動化されるが、タグ付けはマージ後に行うためスキル実行時点では手順1までにとどまる

本番へ反映する際は、[ビルド](#ビルド)と[本番環境へのアップロード](#本番環境へのアップロード)を行い、[公開後の確認](#公開後の確認)に進む。

### ビルド

```bash
npm run build
```

- `dist/` フォルダが生成される
- マスタデータは `src/data/` から直接バンドルされる（Viteビルド時に自動的にバンドル化される）
- `prebuild` / `predeploy` で `npm run validate:data`（マスタデータ整合性チェック）が自動実行される。参照整合性・ID一意性に違反があるとビルド・デプロイが中断する

### 本番環境へのアップロード

Lolipopへの静的ファイルアップロード:

- `dist/` フォルダの内容を本番サーバーにアップロード
- マスタデータはアプリケーションコードにバンドルされているため、アプリバージョンと常に同期される
- ネットワークリクエスト不要でマスタデータが即座に読み込まれる

### 公開後の確認

- [ ] `package.json`・About・CHANGELOG・タグ・GitHub Releaseの版数が一致すること
- [ ] 本番の更新日・告知が、同梱データの更新記録と一致すること

## トラブルシューティング

### マスタデータバリデーションエラー

起動時にバリデーションエラーが発生した場合:

1. ブラウザのコンソールでエラーログを確認
1. `docs/schema.md` でフィールド定義を確認
1. 該当JSONファイルを修正
1. アプリを再起動してエラーが解消されたか確認

### ユーザーデータ破損

LocalStorageに保存されたユーザーデータが破損した場合:

- アプリは自動的に破損データを削除する
- Global Warning Bannerに削除されたアイテムの詳細が表示される
- ユーザーはエクスポート機能でバックアップを取ることを推奨
